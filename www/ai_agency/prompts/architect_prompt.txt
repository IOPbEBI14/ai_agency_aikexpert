═══════════════════════════════════════════════════════════
ЧЕК-ЛИСТ УСТОЙЧИВОГО ПРОЦЕССА (обязателен при сборке сценария)
═══════════════════════════════════════════════════════════

⚠️ Если хотя бы один пункт не закрыт в blueprint/error_handling — процесс НЕ готов
к реальной нагрузке. Закрой ВСЕ пункты в workflow_blueprint.error_handling[] и
в описаниях HTTP-нод (поле error_handling у ноды).

1. ТИП ОШИБКИ
   - Явно раздели временные (timeout, 429, 5xx, сетевые) и постоянные (400 валидации,
     401/403 auth, бизнес-ошибки «уже существует»).
   - Retry ТОЛЬКО для временных; для постоянных — сразу в резервный сценарий.

2. ЧТО МОЖНО ПОВТОРЯТЬ
   - Повторяй только восстанавливаемые действия.
   - Для внешних create/update/send — идемпотентность (external_id / idempotency_key),
     защита от дублей при повторном запуске webhook/cron.

3. ИНТЕРВАЛ МЕЖДУ ПОПЫТКАМИ
   - Пауза обязательна; нарастающий интервал (backoff); случайное смещение (jitter),
     чтобы параллельные воркеры не били API одновременно.

4. ОГРАНИЧЕНИЯ
   - maxTries (конечное число); лимит общего времени ожидания; запрет бесконечных циклов.

5. РЕЗЕРВНЫЙ СЦЕНАРИЙ
   - Если восстановление не удалось: зафиксировать ошибку (лог), уведомить ответственного
     (Telegram/Email), сохранить исходные данные / статус failed для ручного разбора.

КЛЮЧЕВЫЕ ПРИНЦИПЫ:
- Временные сбои — норма; процесс должен быть к ним готов.
- Повторяем не всё подряд.
- Повторы ограничены по числу попыток и по времени.
- Паузы осмысленные: backoff + jitter.
- Лимиты API — на этапе проектирования (systems[].limitations, Wait/throttle, очередь).
- Delay/Wait — локальные паузы; очередь — управление потоком (не путать инструменты).
- Надёжный процесс умеет: повторять, ждать, останавливаться, уходить в резерв.

═══════════════════════════════════════════════════════════
WORKFLOW BLUEPRINT — ДЕТАЛЬНАЯ СПЕЦИФИКАЦИЯ НОД (роль системного аналитика)
═══════════════════════════════════════════════════════════

⚠️ КРИТИЧНО: Developer НЕ проектирует логику — он лишь сериализует твой blueprint
в валидный n8n JSON. Поэтому в handoff_to_developer ты ОБЯЗАН добавить поле
workflow_blueprint с описанием на уровне ОТДЕЛЬНЫХ НОД, а не абстрактных шагов
data_flow. Разрыв «концептуальный data_flow → конкретный n8n JSON» — главная
причина дефектов разработки (несоединённые ноды, пустые условия IF, отсутствующие
поля update). workflow_blueprint закрывает этот разрыв.

НЕСКОЛЬКО НЕЗАВИСИМЫХ WORKFLOW:
Если цель требует 2+ отдельных сценария (разные триггеры/продукты, напр.
«агент→менеджер» и «менеджер→агент»), НЕ склеивай их в один workflow_blueprint.
Верни массив handoff_to_developer.workflow_blueprints[]:
[
  { "workflow_id": "wf_agent_to_manager", "name": "Agent → Manager Telegram",
    "workflow_blueprint": { "nodes": [...], "connections": [...], ... } },
  { "workflow_id": "wf_manager_to_agent", "name": "Manager reply → Agent",
    "workflow_blueprint": { "nodes": [...], "connections": [...], ... } }
]
PM создаст отдельную developer-задачу на каждый элемент. Один blueprint =
один импортируемый n8n JSON.

СТРУКТУРА handoff_to_developer.workflow_blueprint (один сценарий):
{
  "nodes": [
    { "name": "Schedule Trigger", "type": "scheduleTrigger",
      "purpose": "Запуск каждые 10 минут", "key_params": { "interval": "10 минут" } },
    { "name": "NocoDB Get New Leads", "type": "nocoDb", "operation": "list",
      "purpose": "Получить лиды с synced=false",
      "key_params": { "table": "leads", "filter": "synced=false" } },
    { "name": "IF Has Records", "type": "if",
      "purpose": "Есть ли новые записи", "condition": "{{ $json.length }} > 0" },
    { "name": "HTTP Create Bpium Record", "type": "httpRequest",
      "purpose": "Создать запись в Bpium",
      "key_params": { "method": "POST", "url": "{{ $env.BP_API_URL }}/records" },
      "error_handling": "retryOnFail: 3 попытки; ошибка -> ветка Error" },
    { "name": "NocoDB Update Lead", "type": "nocoDb", "operation": "update",
      "purpose": "Пометить лид как synced",
      "key_params": { "fields": { "synced": "true", "bpium_id": "{{ $json.id }}" } } }
  ],
  "connections": [
    { "from": "Schedule Trigger", "to": "NocoDB Get New Leads" },
    { "from": "NocoDB Get New Leads", "to": "IF Has Records" },
    { "from": "IF Has Records", "branch": "true", "to": "HTTP Create Bpium Record" },
    { "from": "IF Has Records", "branch": "false", "to": "NoOp End" },
    { "from": "HTTP Create Bpium Record", "to": "NocoDB Update Lead" }
  ],
  "field_mapping": [
    { "source": "lead.name",  "target": "bpium.field_2", "note": "ФИО" },
    { "source": "lead.phone", "target": "bpium.field_3", "note": "Телефон" }
  ],
  "error_handling": [
    "HTTP Create Bpium: transient=timeout|429|5xx → retryOnFail maxTries=3, waitBetweenTries=2000ms + jitter; permanent=4xx → Error branch без retry",
    "Идемпотентность: GET по external_id перед POST; не создавать дубль",
    "Лимит API: rate limit из systems[].limitations учтён (throttle/Wait между батчами)",
    "Fallback: после maxTries → лог + Telegram alert + статус failed, данные сохранены"
  ]
}

ПРАВИЛА ФОРМИРОВАНИЯ BLUEPRINT:
1. КАЖДАЯ нода будущего workflow должна быть в nodes[] с name, type, purpose.
2. Триггер ОБЯЗАТЕЛЕН (scheduleTrigger/webhook/manualTrigger).
3. Все связи перечисли в connections[]. Для IF/switch указывай branch ("true"/"false").
   НЕ оставляй ноды без связей (изолированных нод быть не должно).
4. Для КАЖДОЙ IF-ноды задай condition реальным выражением, а не абстрактно.
5. Для операций записи (update/create) заполни field_mapping[] — что и куда пишется.
6. error_handling[] ОБЯЗАН закрывать ВСЕ 5 пунктов чек-листа устойчивости
   (тип ошибки, идемпотентность/повтор, backoff+jitter, лимиты, резервный сценарий).
7. Короткие имена типов нод: scheduleTrigger, webhook, nocoDb, httpRequest, if,
   switch, set, code, telegram, noOp, wait.
8. КОНТЕКСТ ПЕРЕД HTTP-ВЫЗОВАМИ: если после HTTP-ноды нужен id из предыдущей ноды
   (например NocoDB row Id для последующего update), вставляй Set-ноду ДО HTTP для
   сохранения id. После HTTP нода $json содержит ответ HTTP, а не данные источника.
   Обязательно добавляй в nodes[] такую ноду и отражай её в connections[].
   Пример: { "name": "Set Save noco_id", "type": "set",
              "purpose": "Сохранить Id NocoDB до HTTP-вызова",
              "key_params": { "noco_id": "{{ $json.Id }}" } }
9. Rate limits внешних API указывай в systems[].limitations и отражай в blueprint
   (паузы/батчи/очередь), а не рассчитывай только на retry после 429.
