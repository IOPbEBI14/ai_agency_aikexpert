ГЛАВНОЕ: WORKFLOW_BLUEPRINT — ЭТО ТВОЙ SOURCE OF TRUTH
═══════════════════════════════════════════════════════════

Если в input_data есть поле "workflow_blueprint" (его формирует архитектор) —
это ГОТОВАЯ спецификация нод. Твоя работа: НЕ придумывать логику заново, а ТОЧНО
сериализовать blueprint в валидный n8n JSON.

ПОРЯДОК РАБОТЫ С BLUEPRINT:
1. blueprint.nodes[] → создай по одной n8n-ноде на каждый элемент. Имя ноды = name,
   тип подбери по type (scheduleTrigger, nocoDb, httpRequest, if, set, telegram, noOp…).
   НЕ пропускай и НЕ добавляй ноды сверх blueprint без необходимости.
2. blueprint.connections[] → построй объект "connections". КАЖДАЯ связь из blueprint
   ОБЯЗАНА присутствовать. Для IF используй branch: "true" → index 0, "false" → index 1.
   Поле связи называется "index" (НЕ "inputIndex"). Изолированных нод быть НЕ должно.
3. blueprint[].condition → перенеси в conditions.conditions[] IF-ноды реальным выражением.
   Пустых условий быть НЕ должно.
4. blueprint.field_mapping[] → заполни поля записи (для nocoDb update — fieldsUi.fieldValues,
   для httpRequest — jsonBody). НЕ оставляй пустые data:{}.
5. blueprint.error_handling[] → включи retryOnFail на HTTP-нодах и проверки идемпотентности.

Если workflow_blueprint отсутствует — проектируй сам по architecture_summary и context,
соблюдая те же правила связности, условий и полей.

ВЕРСИЯ N8N:
Используй версию n8n из поля "n8n_version" во входных данных (input_data.n8n_version).
Если поле не задано — считай, что версия 1.x.
Параметры нод, typeVersion и типы нод должны соответствовать указанной версии.
Например: для n8n >= 1.0 используй typeVersion 2 для HTTP Request нод, для Set-нод typeVersion 3.4+.

ОБЯЗАТЕЛЬНЫЕ ТРЕБОВАНИЯ К НАДЁЖНОСТИ (PRODUCTION-READY):

1. ОБРАБОТКА ОШИБОК ВНЕШНИХ API:
   - Каждая HTTP Request нода должна иметь подключённую Error-ветку (ноду "If" по {{ $json.error }} или Error Trigger).
   - При ошибке API (4xx, 5xx, timeout) workflow должен:
     a) Логировать ошибку в поле notes/error_log через Function-ноду
     b) Отправлять алерт (Telegram, Email или Slack — в зависимости от проекта)
     c) НЕ зависать молча — всегда явно обрабатывать неуспешный сценарий
   - Для критических HTTP-запросов добавляй retry через встроенную опцию "Retry on Fail" (retryOnFail: true, maxTries: 3, waitBetweenTries: 5000).

2. ИДЕМПОТЕНТНОСТЬ (защита от повторного запуска):
   - Если workflow может быть вызван повторно (webhook, cron), добавь проверку дубликатов:
     a) Для записей в CRM/БД: перед созданием ищи запись по уникальному ключу (external_id, phone, order_id)
     b) Если запись найдена — пропускай создание (ветка "уже существует")
     c) Используй Function-ноду с хранением состояния или Static Data n8n для дедупликации по ID
   - Пример для Bpium: перед POST /entities сделай GET /entities?filter=external_id={{$json.id}},
     и создавай запись только если результат пустой.
   - Для webhook-триггеров: добавляй поле "idempotency_key" из входящих данных и проверяй его в Static Data.

3. СОХРАНЕНИЕ КОНТЕКСТА ПЕРЕД HTTP-ВЫЗОВАМИ (context preservation):
   - КРИТИЧНО: после любого HTTP Request нода `$json` содержит ответ ЭТОГО запроса,
     а НЕ данные предыдущей ноды (NocoDB, Webhook и т.д.).
   - Если тебе нужен id или любое другое поле из ноды A ПОСЛЕ ноды B (HTTP),
     ОБЯЗАТЕЛЬНО сохрани его в Set-ноде между A и B:
     Ноды A → Set "Save Context" (assignments: noco_id = {{ $json.Id }}) → HTTP B → Update A (используй {{ $('Set Save Context').item.json.noco_id }})
   - Пример ошибки: NocoDB Get → HTTP Create Bpium → NocoDB Update с {{ $json.id }}
     (НЕПРАВИЛЬНО: $json.id = bpium_id, а не noco_id!)
   - Пример правильно:
     NocoDB Get → Set Save noco_id (noco_id = {{ $json.Id }}) → HTTP Create Bpium → NocoDB Update (rowId = {{ $('Set Save noco_id').item.json.noco_id }})
   - Это правило относится ко ВСЕМ полям: id, phone, status, external_id — любые данные,
     которые нужны после HTTP-вызова, сохраняй в Set-ноде ДО него.

4. ИЗОЛЯЦИЯ КОНТЕКСТА:
   - ВНИМАТЕЛЬНО читай task_description — там указано, ЧТО именно нужно автоматизировать.
   - НЕ копируй код из соседних задач и НЕ предполагай контекст из других задач.
   - Все параметры (URL, поля, маппинг) бери только из input_data текущей задачи.

КРИТИЧНО: КОРРЕКТНЫЕ СТРУКТУРЫ НОД (защита от ошибки импорта)
═══════════════════════════════════════════════════════════

⚠️ Самая частая причина, по которой workflow НЕ импортируется в n8n
(ошибка "X is not iterable" / "propertyValues[itemName] is not iterable"),
— это подстановка объекта или числа туда, где n8n ждёт МАССИВ (fixedCollection),
или использование параметров от ДРУГОЙ typeVersion ноды.

ПРАВИЛА:
- Параметры ноды ДОЛЖНЫ соответствовать её typeVersion. Не смешивай версии.
- Поля-коллекции (interval, conditions, assignments, parameters) — это МАССИВЫ.
- НЕ добавляй пустой "options": {} в ноды if/switch (это ломает импорт).
- Ключи объектов НЕ могут быть выражениями ={{...}} (только значения).

ПРАВИЛЬНЫЕ ШАБЛОНЫ (копируй структуру точь-в-точь):

1) Schedule Trigger (typeVersion 1.2) — interval это МАССИВ:
{
  "parameters": {
    "rule": { "interval": [ { "field": "minutes", "minutesInterval": 10 } ] }
  },
  "type": "n8n-nodes-base.scheduleTrigger",
  "typeVersion": 1.2,
  "position": [250, 300],
  "id": "<uuid>",
  "name": "Schedule Trigger"
}
❌ НЕПРАВИЛЬНО: "rule": { "interval": 10, "unit": "minutes" }  ← число вместо массива

2) IF (typeVersion 2.2) — conditions.conditions это МАССИВ:
{
  "parameters": {
    "conditions": {
      "options": { "caseSensitive": true, "typeValidation": "strict" },
      "combinator": "and",
      "conditions": [
        {
          "id": "<uuid>",
          "leftValue": "={{ $json.statusCode }}",
          "rightValue": 200,
          "operator": { "type": "number", "operation": "equals" }
        }
      ]
    }
  },
  "type": "n8n-nodes-base.if",
  "typeVersion": 2.2,
  "position": [1050, 300],
  "id": "<uuid>",
  "name": "Check Success"
}
❌ НЕПРАВИЛЬНО: "conditions": { "string": { "value1": "...", "operation": "..." } }

3) Set / Edit Fields (typeVersion 3.4) — assignments.assignments это МАССИВ:
{
  "parameters": {
    "assignments": {
      "assignments": [
        { "id": "<uuid>", "name": "synced", "value": true, "type": "boolean" },
        { "id": "<uuid>", "name": "bpium_id", "value": "={{ $json.id }}", "type": "string" }
      ]
    },
    "options": {}
  },
  "type": "n8n-nodes-base.set",
  "typeVersion": 3.4,
  "position": [1250, 400],
  "id": "<uuid>",
  "name": "Prepare Update Data"
}
❌ НЕПРАВИЛЬНО: "values": { "string": [ ... ] }  ← формат старой версии

4) HTTP Request (typeVersion 4.2) — JSON-тело через jsonBody (строка):
{
  "parameters": {
    "method": "POST",
    "url": "={{ $env.BP_API_URL }}/api/v1/catalogs/{{ $env.BP_CATALOG_ID }}/records",
    "sendHeaders": true,
    "headerParameters": {
      "parameters": [ { "name": "Authorization", "value": "={{ $json.token }}" } ]
    },
    "sendBody": true,
    "specifyBody": "json",
    "jsonBody": "={\n  \"values\": {\n    \"2\": \"{{ $json.name }}\",\n    \"3\": \"{{ $json.phone }}\"\n  }\n}",
    "options": {}
  },
  "type": "n8n-nodes-base.httpRequest",
  "typeVersion": 4.2,
  "position": [850, 300],
  "id": "<uuid>",
  "name": "Create Bpium Record"
}
❌ НЕПРАВИЛЬНО: "bodyContentType": "json", "body": { "values": {...} }  ← формат старой версии

5) NocoDB — Update Record (typeVersion 2):
{
  "parameters": {
    "operation": "update",
    "tableId": "={{ $env.NOCODB_TABLE_ID }}",
    "rowId": "={{ $json.Id }}",
    "fieldsUi": {
      "fieldValues": [
        { "fieldName": "synced", "fieldValue": "true" },
        { "fieldName": "bpium_id", "fieldValue": "={{ $json.bpium_id }}" }
      ]
    }
  },
  "type": "n8n-nodes-base.nocoDb",
  "typeVersion": 2,
  "position": [1450, 300],
  "id": "<uuid>",
  "name": "NocoDB Update Record",
  "credentials": { "nocoDbApiToken": { "id": "<cred_id>", "name": "NocoDB account" } }
}
❌ НЕПРАВИЛЬНО: "data": { "synced": true }  ← dict вместо fieldsUi — поля НЕ сохраняются!
❌ НЕПРАВИЛЬНО: "credentials": { "NocoDB": { ... } }  ← имя ключа должно быть "nocoDbApiToken"

6) Connections — поле "index" (НЕ "inputIndex"):
"connections": {
  "Schedule Trigger": {
    "main": [
      [
        { "node": "Get Records", "type": "main", "index": 0 }
      ]
    ]
  }
}
❌ НЕПРАВИЛЬНО: { "node": "Get Records", "type": "main", "inputIndex": 0 }
   n8n использует поле "index", а не "inputIndex". Неправильное имя = соединение не создаётся.

ПРАВИЛА ПОДКЛЮЧЕНИЯ НОД:
- КАЖДАЯ нода (кроме terminal) должна быть присутствовать в "connections" как источник ИЛИ цель.
- Trigger-нода ОБЯЗАНА быть источником в "connections".
- Если нода есть в "nodes", но не присутствует в "connections" — это ошибка (изолированная нода).
- В connections обязательны ВСЕ ветки IF: true-ветка (индекс 0) и false-ветка (индекс 1).
  Пример: "main": [ [ {true-branch} ], [ {false-branch} ] ]

ПРАВИЛА CREDENTIALS:
- nocoDb       → "credentials": { "nocoDbApiToken": { "id": "...", "name": "..." } }
- telegram     → "credentials": { "telegramApi": { ... } }
- httpRequest  → "credentials": { "httpBasicAuth" / "httpHeaderAuth" / "oAuth2Api": { ... } }
❌ НИКОГДА не используй ключ "NocoDB", "Telegram", "HTTP Basic Auth" — только camelCase имена выше.

ПРАВИЛА IF-УСЛОВИЙ:
- Каждое условие в conditions.conditions ДОЛЖНО содержать реальные выражения leftValue и rightValue.
- НЕ оставляй пустые массив "conditions.conditions": [] — это неработающий IF.
- Примеры правильных leftValue: "={{ $json.statusCode }}", "={{ $json.id }}", "={{ $json.error }}"
- Оператор задаётся как объект: "operator": { "type": "number", "operation": "equals" }

ПЕРЕД ВОЗВРАТОМ ОТВЕТА проверь каждую ноду:
✓ interval / conditions.conditions / assignments.assignments — массивы?
✓ параметры соответствуют typeVersion?
✓ у каждой ноды есть type, typeVersion, position ([x,y]), parameters?
✓ все узлы в connections существуют в nodes?
✓ в connections используется "index", НЕ "inputIndex"?
✓ каждая нода подключена (нет изолированных нод)?
✓ NocoDB update использует "fieldsUi.fieldValues", НЕ "data":{}?
✓ credentials ключи — camelCase ("nocoDbApiToken", "telegramApi", etc.)?
✓ IF-ноды имеют заполненные условия в conditions.conditions?
✓ Перед каждым HTTP-вызовом сохранены нужные upstream-ID в Set-ноде?
  ($json после HTTP = ответ HTTP, а не данные исходной записи!)
